# Отчёт vserence

Отчёт пишется для человека, который не видел код, и первым делом говорит, что проверено, а что нет. По одному отчёту, без доступа к коду, человек отвечает на три вопроса: что изменилось, как это проверено, что осталось непроверенным.

Шаблон: `${CLAUDE_PLUGIN_ROOT}/templates/report.md`. Разделы и их порядок не меняются, ни один не удаляется.

## Как заполнять

- **Итог.** `Режим: <режим> · Ветка: vserence/<задача> · Уверенность: высокая | средняя | низкая`. Если режим менялся, укажи `fix → feature (<причина: слова пользователя или новое поведение>)`. Если в fix сработали триггеры анализа рисков, укажи их. Для остановленной задачи добавь строку `Статус: не завершено — <причина из state.json>` и список открытых проблем.
- **Что сделано.** Один абзац простыми словами, без терминов: что теперь работает иначе для пользователя или системы.
- **Почему так.** Выбранный вариант и отброшенные, по одной фразе на каждый.
- **Изменённые файлы.** `файл — зачем изменён`, по строке на файл; сгенерированные файлы одной строкой.
- **Как проверено.** Какие поведения покрыты тестами (по названиям тестов), какие моки и на каких границах, результат каждой команды из `checks.json` (зелёная / красная / нет команды), результат мутаций (доля убитых мутантов или 2–3 ручные поломки ревьюера и упали ли тесты), вердикт ревью и число скрытых приёмочных тестов. Добавленные онбордингом проверки называются здесь. Из `state.json` → `baseline_report`: «падали до задачи» (известные падения из baseline, не красные), «починены тесты из baseline» (это прогресс), либо «сравнение с baseline не выполнено — <причина>».
- **Риски из каталога.** Каждый риск из `risks-analysis.md`: `покрыт тестом <имя теста>` / `не применим — <почему>` / `не покрыт — <почему>`.
- **Записанные правила.** Список из `rules.md` / раздела «Записанные правила» `risks-analysis.md`: `правило — файл:строка — соответствует | противоречит (вопрос задан, ответ: …) | не затрагивает`. Ни одного правила не найдено — так и напиши, с перечнем мест, где искал.
- **Что НЕ проверено.** Честный список: команды, которых нет в `checks.json`; непокрытые риски; e2e/мутации, которые не запускались; поведение, которое не удалось запустить. Пустым он бывает редко; если пуст — напиши, почему.
- **Что посмотреть глазами.** 2–3 места в diff (`файл:строка`), где нужно решение человека, и вопрос к каждому.
- **Стоимость.** Токены (если известны, иначе «не измерено»), время, циклы исправлений после проверок (`check_cycles`) и после ревью (`review_cycles`) из `state.json`.

## Уверенность (ровно по условиям)

| Уровень | Условие |
| --- | --- |
| высокая | все команды из `checks.json` существуют и зелёные; ревью без блокирующих замечаний; все применимые риски покрыты тестами |
| средняя | есть непокрытые риски с обоснованием, или нет e2e и мутаций там, где они положены |
| низкая | в проекте нет тестов или проверок, или изменение не удалось запустить, или статус «не завершено» |

Если не выполнено условие «высокой» и не подходит «низкая» — уровень «средняя».

## Режим investigate

Отчёт содержит те же разделы; «Что сделано» = результат investigate: гипотезы по убыванию вероятности; для каждой доказательство (замер, строка лога, место в коде) и способ проверить; рекомендуемая следующая задача с режимом. «Изменённые файлы» = нет (правки кода запрещены).

## Вывод

- Полный отчёт — в `.vserence/tasks/<задача>/report.md`, коммит в ветку задачи; если настроен `gh` или `glab` — в описание PR.
- В сессию выведи только «Итог», «Что сделано», «Что НЕ проверено» и путь к полному отчёту.
- Содержимое файлов секретов в отчёт не попадает никогда.
