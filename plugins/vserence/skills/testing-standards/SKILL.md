# Стандарт тестирования

Тесты выбираются по риску, а не по проценту покрытия, и защищены от подгонки: агенты склонны проходить видимые тесты, подделывая результат, и чаще людей добавляют моки (36% коммитов против 26%). Надстройка над скиллом `superpowers:test-driven-development`.

## Что покрывать обязательно
- бизнес-правила и расчёты: деньги, статусы, права, лимиты;
- границы системы: API, разбор внешних данных (фиды, вебхуки, файлы), схема БД;
- сценарии из каталога рисков (`risks-analysis.md`);
- каждый исправленный баг;
- переходы состояний и конкурентность;
- критичные пользовательские пути из `project.md` (до 5) end-to-end.

## Что не покрывать
Поведение фреймворка и библиотек; тривиальный код (геттеры, перекладывание полей, конфиги); приватные детали реализации; сгенерированный код; вёрстку попиксельно (для UI — визуальные проверки); одно поведение на нескольких уровнях сразу.

## Принципы (как тестировать)
1. Поведение через публичный интерфейс, чтобы тесты переживали рефакторинг.
2. Один тест = одно поведение; название описывает его предложением.
3. Детерминизм: время, случайность и сеть подставляются.
4. Моки только на границах, которыми проект не владеет (внешние API, почта, платёжка); своя БД и свой код — по-настоящему.
5. Много быстрых тестов на логику, меньше интеграционных, единицы end-to-end.
6. Нестабильный тест считается багом.
7. Скорость: `test_changed` ≤ 60 секунд, полный набор unit ≤ 5 минут. Если нет — хуки гоняют только `test_changed`, полный набор запускается один раз перед отчётом.

## Защита от подгонки
1. Тесты пишутся из спецификации до кода, падают по правильной причине и коммитятся отдельно.
2. На этапе кода тесты заморожены хуком. Неверный тест = остановка и объяснение в отчёте.
3. Stop-хук по diff запрещает `skip`, `only`, `xfail`, удаление тестов, ослабление проверок (уменьшение числа утверждений), ветки «если тестовое окружение» в рабочем коде.
4. Ревьюер пишет скрытые приёмочные тесты по спецификации, не видя тестов исполнителя.
5. На изменённом коде критичных модулей — мутационное тестирование, порог 70% убитых мутантов (Stryker, mutmut, PIT, cargo-mutants). Нет инструмента → ревьюер сам вносит 2–3 поломки и проверяет, что тесты падают.
6. Каждый мок собственного кода ревьюер помечает как замечание (в критичном модуле — блокирующее).

## Как проверить
- [ ] Для каждого критерия приёмки и каждого риска из `risks-analysis.md` есть тест (по плану) или обоснование.
- [ ] Тестовый коммит идёт раньше коммита с кодом; на тестовом коммите новые тесты красные по причине «нет поведения».
- [ ] В fix есть тест, который падает без исправления и проходит с ним.
- [ ] Нет моков модулей самого проекта; моки только для внешних границ.
- [ ] В тестах нет реального времени/случайности/сети без подстановки (`now()`, `random`, HTTP к внешним хостам).
- [ ] Имя каждого нового теста — предложение о поведении.
- [ ] `test_changed` ≤ 60 с, unit ≤ 5 мин (время из вывода).

## Антипаттерны
- Тест повторяет реализацию (проверяет вызовы приватных методов, порядок внутренних шагов).
- Мок своего репозитория/сервиса вместо настоящей тестовой БД.
- `sleep` вместо управляемых часов; повтор упавшего теста вместо исправления нестабильности.
- Подгонка ожидаемого значения под фактический результат.
- Один тест проверяет пять поведений.

## Плохо / хорошо
```text
ПЛОХО: мок своего кода, проверка реализации
  test "order":
    repo = mock(OrderRepo); repo.save.returns(ok)
    service.place(order); assert repo.save.calledOnce
ХОРОШО: поведение через публичный интерфейс, настоящая БД, мок только внешней платёжки
  test "placing an order with a declined card leaves it unpaid":
    payments = fakePaymentGateway(declines = true)
    id = api.placeOrder(cart, payments)
    assert api.getOrder(id).status == "unpaid"
```
```text
ПЛОХО: test "discount" { assert calc(now()) > 0 }
ХОРОШО: test "discount is 10% on Black Friday" { clock = fixed("2026-11-27"); assert calc(100, clock) == 90 }
```
