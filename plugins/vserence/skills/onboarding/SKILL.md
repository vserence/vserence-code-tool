# Онбординг и синхронизация контракта

Контракт делает результат независимым от того, кто писал проект: любой репозиторий приводится к одному формату.
Шаблоны: `${CLAUDE_PLUGIN_ROOT}/templates/`. Скрипт состояния: `node "${CLAUDE_PLUGIN_ROOT}/hooks/scripts/vserence-state.js"`.

## Контракт `.vserence/` (лимиты обязательны)

| Файл | Содержимое | Лимит |
| --- | --- | --- |
| `project.md` | назначение, стек, модули, кто кого вызывает, где данные, внешние интеграции, список критичных модулей, до 5 критичных пользовательских путей | ~3 КБ |
| `checks.json` | команды `format`, `lint`, `typecheck`, `test`, `test_changed`, `build`, `e2e`, `mutation` + тихие варианты (`quiet`) | — |
| `conventions.md` | имена, структура, обработка ошибок, коммиты; разделы «Секреты», «Пути тестов», «Продакшен», «Настройки сборки» | ~2 КБ |
| `risks.md` | риски именно этого проекта, растут через постмортемы | ~3 КБ, дальше делится на `risks/<домен>.md` |
| `decisions/` | короткие записи архитектурных решений, читаются по требованию | по файлу на решение |

Запрещено: история работы в контракте (она в git); постоянно растущие журналы в загружаемых файлах; секреты и пароли на любом уровне (только указание, где они лежат).
**Критичный модуль** = код, который работает с деньгами, правами доступа, персональными данными, удалением данных или внешними интеграциями.

## Режим «онбординг» (контракта нет)

1. **Исследуй проект в сабагентах.** Запусти сабагент `vserence:explorer` (модель haiku) по каждому направлению отдельно: манифесты зависимостей; структура папок; CI; точки входа; связи модулей (кто кого вызывает, где данные, внешние интеграции). Каждый возвращает одну страницу выводов. Сам десятки файлов не читай.
2. **Найди и сожми существующие источники:** `AGENTS.md`, `CLAUDE.md`, правила Cursor (`.cursorrules`, `.cursor/rules/`), memory bank, README, `docs/`. Перенеси факты в контракт сжато. Оригиналы не удаляй.
3. **Определи команды проверок** и запусти каждую, чтобы убедиться, что она работает (exit 0 на текущем коде, либо зафиксируй, что падает и почему). Для каждой задай `quiet`-вариант: выводит только ошибки и итог. `test_changed` принимает `{files}` или сам находит изменённое. Нет проверки → добавь минимальный набор: стандартные для стека форматтер и линтер, проверку типов для типизированных языков, один smoke-тест запуска приложения. Каждую добавленную проверку назови в отчёте. Замерь время `test_changed` и полного unit-набора: пороги 60 с и 5 мин; превышение запиши в отчёт.
4. **Составь карту архитектуры** и запиши в `project.md`: модули, связи, данные, интеграции, критичные модули, до 5 критичных пользовательских путей.
5. **Разложи найденное по уровням** (правило ниже), создай из шаблонов `AGENTS.md`, `CLAUDE.md` (ровно одна строка `@AGENTS.md`), `.claude/settings.json`, правила подпапок (`<модуль>/AGENTS.md` или `.claude/rules/*.md` с `paths:`), шаблон Local (`CLAUDE.local.md`, `.claude/settings.local.json`) и добавь оба Local-файла в `.gitignore`. Если `CLAUDE.md` уже есть с содержимым — перенеси правила в `AGENTS.md`, оставь в `CLAUDE.md` одну строку `@AGENTS.md`.
6. Выполни `vserence-state.js snapshot` (снимок манифестов, CI и папок первого уровня для SessionStart-хука) и `vserence-state.js context` (бюджет постоянного контекста ≤ 8000 токенов; больше → сокращай AGENTS.md, переноси детали в файлы «читай по требованию»).
7. **Покажи контракт одним диффом вместе с первым отчётом** и продолжи исходную задачу: контракт попадает отдельным первым коммитом `vserence: контракт проекта` в ветку задачи. Если онбординг вызван без задачи (`/vserence:init`), создай ветку `vserence/init-contract` (`git checkout -b`), закоммить туда и выведи краткий отчёт по шаблону.

**Проект с нуля** (пустой репозиторий): задай вопросы о продукте и ограничениях (одним сообщением, не больше трёх, с вариантами ответа), создай контракт и каркас с проверками до первой строки бизнес-логики. Дальше работает режим greenfield роутера.

## Режим «синхронизация» (контракт устарел или превышен бюджет)

То же самое, но только для изменившегося: SessionStart-хук перечислил причины (версия контракта, манифесты, CI, папки первого уровня, бюджет). Обнови только затронутые разделы: новые зависимости, модули, команды. Дополнительно:
- найди дубли между уровнями (User, Project, подпапки, Local) и оставь факт на одном уровне;
- проверь лимиты файлов контракта и бюджет постоянного контекста; превышение `risks.md` → раздели на `risks/<домен>.md`;
- при смене `contract_version` приведи файлы к формату шаблонов текущей версии плагина;
- в конце `vserence-state.js snapshot`. Изменения коммить в ветку текущей задачи (или `vserence/sync-contract`, если задачи нет).

## Правило раскладки по уровням

- правда для всех проектов и для меня → User (`~/.claude/CLAUDE.md`, до 10 строк: язык общения, стиль отчёта);
- правда для всех в этом проекте → Project (`AGENTS.md`, `.vserence/`, `.claude/settings.json`);
- правда только для части кода → подпапка (`<модуль>/AGENTS.md`) или `.claude/rules/*.md` с путями;
- правда только для меня в этом проекте → Local (`CLAUDE.local.md`, `.claude/settings.local.json`).

Запреты: один факт на двух уровнях; факты о проекте на уровне User; секреты на любом уровне.

## Совместимость с Codex

Текст правил пишется в `AGENTS.md`, `CLAUDE.md` содержит одну строку `@AGENTS.md`. Codex читает `AGENTS.md` и `.vserence/` без установки, без хуков и автоматики.

## Проверка результата онбординга (все пункты обязательны)

- [ ] 5 файлов контракта существуют и укладываются в лимиты (`wc -c`).
- [ ] Каждая команда в `checks.json` запущена; результат и время записаны в отчёт; отсутствующие = `null` и названы в «Что НЕ проверено».
- [ ] `CLAUDE.md` = одна строка `@AGENTS.md`.
- [ ] Ни одного абсолютного пути и имени пользователя в контракте и `AGENTS.md`.
- [ ] `vserence-state.js context` ≤ 8000 токенов.
- [ ] `.vserence/sync-state.json` создан.
