# Роутер vserence

Скрипт состояния (единственный способ менять `state.json`): `node "${CLAUDE_PLUGIN_ROOT}/hooks/scripts/vserence-state.js" <команда>` — ниже `STATE`.
Приоритет: этот роутер важнее общих правил `superpowers:using-superpowers`. Скилл `superpowers:brainstorming` в конвейере не вызывается никогда (его заменяет spec.md), даже если using-superpowers требует его «перед любой работой».
Файлы задачи: `.vserence/tasks/<имя>/` (spec.md, plan.md, risks-analysis.md, review.md, report.md). Они коммитятся в ветку задачи и никогда не читаются в других задачах.

## Обязательно, без исключений
- **Размер задачи определяет режим, но не отменяет этапы режима.** Маленькая правка = режим fix со всеми его этапами: записанные правила, тест, код, проверки, ревью, отчёт. Пропускать этап (онбординг, `start`, записанные правила, спецификацию, анализ рисков, тесты, ревью, отчёт) по своему суждению о размере, срочности или очевидности нельзя.
- **Ревьюер `vserence:reviewer` обязателен во всех режимах, кроме investigate.**
- Хуки работают fail-closed: после сообщения-задачи, пока не выполнен `STATE start`, правки кода и остановка заблокированы; остановка без `report.md` заблокирована. Обходить блокировку (другим инструментом, скриптом, через переменные) нельзя: причина блокировки — следующий шаг конвейера.

## 1. Подготовка
1. **Нет `.vserence/checks.json` → задача не начинается.** Сначала онбординг по скиллу `vserence:onboarding`. Онбординг не завершён, пока контракт (5 файлов) не записан на диск и не показан человеку списком файлов с кратким содержимым. Только после этого — раздел 2.
2. Если в контексте есть инструкция SessionStart-хука о синхронизации — сначала она.
3. Прочитай раздел `conventions.md` → «Порядок с проектными правилами» и выполняй его: правила проекта, помеченные «сохраняется», выполняются в указанной точке конвейера; помеченные «заменяется конвейером» не выполняются. Если раздела нет, а в `AGENTS.md`/`CLAUDE.md`/`.cursor/rules` есть правила о процессе (ожидание одобрения плана, подтягивание main в рабочую ветку, обязательные пост-шаги), это синхронизация: выполни шаг «Конфликты с проектными правилами» скилла `vserence:onboarding` до начала задачи.

## 2. Разбор задачи
1. Прочитай `.vserence/project.md` и `.vserence/conventions.md` (они короткие). Поиском (Grep/Glob, символы) найди объект изменения; для широкого поиска — сабагент `vserence:explorer`.
2. Выбери режим по таблице. Если режим задан явно (`/vserence <режим> …`), используй его.

| Режим | Когда |
| --- | --- |
| fix | есть наблюдаемый неверный результат, ожидаемое поведение известно, правка в одном модуле без смены контракта |
| feature | появляется новое поведение для пользователя или другой системы |
| refactor | вход и выход системы остаются прежними, меняется устройство кода или скорость |
| greenfield | проект или сервис с нуля |
| investigate | «почему тормозит», «откуда баг», аудит; правки кода запрещены |

3. **Подъём режима.** fix автоматически поднимается до feature, если правка затрагивает хотя бы одно: больше одного модуля из `project.md`, публичный API, схему БД, формат файлов или критичный модуль (список в `project.md`). Режим никогда не опускается. Подъём во время работы: `STATE escalate feature "<какой триггер>"`.
4. **Вопрос** задаётся, только если выполнено хотя бы одно условие:
   1. В задаче не назван объект изменения, и поиск по коду находит больше одного кандидата или ни одного.
   2. У задачи есть две трактовки, которые дают разное поведение для пользователя.
   3. Задача противоречит контракту или записи в `decisions/`.
   4. Нужны данные, которых нет в репозитории: лимиты, доступы, бизнес-правила.
   5. Нужно необратимое действие: удаление данных, миграция с потерей данных, смена публичного API.

   Про имена, стиль и всё, что решается конвенциями проекта, вопросы не задаются. Вопросы — одним сообщением, не больше трёх, у каждого варианты ответа. Перед вопросом всегда выполни `STATE ask` (работает и до `start`; без него Stop-хук не даст остановиться). Это единственная обязательная остановка.
   К условию 3 относятся и правила, записанные вне контракта: `docs/`, ТЗ, `README`, и тесты, закрепляющие решение (раздел «Записанные правила»).
5. **Первая строка работы:** `Режим: <режим> — <почему, одной фразой>`, чтобы человек мог оспорить.
6. Создай задачу и ветку: `STATE start <короткое-имя-латиницей> <режим>` → ветка `vserence/<имя>`. Сборка никогда не мержит в основную ветку и не делает деплой: это решает человек.

## 2a. Записанные правила (все режимы, кроме investigate; до первого изменения кода)
1. Выпиши ключевые сущности задачи (имена модулей, функций, терминов предметной области, например «этаж», «статус», «свободна»).
2. Поиском (Grep, регистр не важен, русские и английские формы) найди упоминания в: `docs/` (включая ТЗ), `.vserence/` (project.md, conventions.md, risks.md, decisions/), `README*`, `AGENTS.md`/`CLAUDE.md`, и в тестах (названия тестов и утверждения про эти сущности).
3. Запиши `.vserence/tasks/<имя>/rules.md`: по строке на правило — `файл:строка — цитата — правка: соответствует | противоречит | не затрагивает`.
4. Правка противоречит записанному правилу или тесту, закрепляющему решение (тест проверяет именно это поведение), → это условие 3: `STATE ask`, вопрос с вариантами («оставить правило» / «изменить правило, правка верна» / другое), конвейер стоит до ответа. Ответ записывается в `spec.md` («Ответы на вопросы») и в `rules.md`. Менять такой тест или правило без ответа человека нельзя.
5. В feature, refactor, greenfield этот шаг выполняет `vserence:risk-analyst` (раздел «Записанные правила» в `risks-analysis.md`); в fix — ты сам, перед тестом.

## 3. Процесс режима

Модели по ролям: исследование кода, онбординг, поиск связей — Haiku (`vserence:explorer`); реализация по плану и режим fix целиком, включая его ревью, — Sonnet; архитектура, план, анализ рисков, ревью в feature, refactor, greenfield — Opus (`vserence:risk-analyst`, `vserence:reviewer`). Переопределение — только в Local.

### fix
0. Раздел 2a «Записанные правила» → `rules.md`. Противоречие → вопрос.
1. Этап `tests`. Вызови скилл `superpowers:systematic-debugging`. Найди первопричину и всех вызывающих (Grep по символу; `vserence:explorer` для широкого поиска).
2. Сначала тест, воспроизводящий симптом: он падает по той причине, что описана в задаче. Закоммить тест отдельно: `test: воспроизведение <симптом>`.
3. `STATE stage code` (тесты заморожены хуком). Исправь в общей точке, а не в месте симптома. Если правка задела триггер подъёма — `STATE escalate feature "<триггер>"` и продолжай по режиму feature.
4. `STATE stage verify` → проверки (раздел 4) → `STATE stage review` → ревью (раздел 5) → `STATE stage report` → короткий отчёт (раздел 6).

### feature
1. Этап `spec`. Напиши `.vserence/tasks/<имя>/spec.md` строго из 5 разделов: (1) цель одной фразой; (2) сценарии: кто, что делает, что получает; (3) критерии приёмки, каждый проверяется тестом или командой; (4) вне рамок: что сознательно не делается; (5) ограничения: лимиты, совместимость, производительность. Скилл `superpowers:brainstorming` не вызывается: его заменяет эта спецификация.
2. Связи и риски по каталогу: сабагент `vserence:risk-analyst` (opus) с именем задачи, режимом, путём к spec.md и списком затронутых направлений (раздел «Стандарты»). Результат — `risks-analysis.md`. Если ответ начинается с `ПРОТИВОРЕЧИЕ (условие 3)` — `STATE ask` и вопрос человеку до плана.
3. `STATE stage plan`. План по скиллу `superpowers:writing-plans`, сохранить в `.vserence/tasks/<имя>/plan.md`. План содержит: список файлов с действием (создать, изменить, удалить); шаги в порядке выполнения; для каждого критерия приёмки и каждого риска из `risks-analysis.md` — тест, который его проверяет. Если `conventions.md` → «Настройки сборки» → «Остановка на утверждение плана: включена» — `STATE ask` и покажи план; иначе не останавливайся. На вопросы выбора внутри скиллов Superpowers отвечай сам по этому роутеру, человеку их не передавай.
4. `STATE stage tests`. Тесты из спецификации и каталога рисков до кода по скиллу `superpowers:test-driven-development`: каждый падает по правильной причине (нет поведения, а не ошибка импорта/синтаксиса); закоммить тесты отдельно `test: <задача>`.
5. `STATE stage code`. Контрольная точка контекста: реализация стартует в новом контексте от файла плана — по скиллу `superpowers:subagent-driven-development`, сабагентам-исполнителям передавай путь к plan.md и `model: "sonnet"`. Тесты заморожены хуком.
6. `STATE stage verify` → проверки → закоммить → `STATE stage review` → ревью → `STATE stage report` → отчёт.

### refactor
Вход и выход системы не меняются.
1. Этап `plan`. Сабагент `vserence:risk-analyst` (без spec.md — передай описание изменения). План по `superpowers:writing-plans` в `plan.md`: порции изменений, после каждой все тесты зелёные.
2. `STATE stage tests`. Зафиксируй поведение: тесты текущего поведения до изменений (через публичный интерфейс); эталонные ответы для всех затронутых входов в `.vserence/tasks/<имя>/baseline/`; для задач на скорость — замер базы: время ответа и память (команда замера, число прогонов, медиана) в `baseline/metrics.md`. Закоммить отдельно. Эти тесты после фиксации не меняются.
3. `STATE stage code`. Меняй порциями по плану (`superpowers:subagent-driven-development`, исполнители с `model: "sonnet"`); после каждой порции запусти полный `test` — все зелёные, иначе порция откатывается или исправляется до перехода к следующей.
4. `STATE stage verify`: повторный замер теми же командами и сверка эталонных ответов (побайтно или по записанному правилу сравнения); результат до/после — в отчёт. Затем ревью и отчёт.

### greenfield
1. Этап `spec`. Вопросы о продукте и ограничениях (одним сообщением, до трёх, с вариантами; `STATE ask`). Затем `spec.md` (5 разделов, как в feature) и архитектура по скиллу `vserence:architecture-principles`: дорогие к отмене решения — в `.vserence/decisions/`.
2. Контракт: скилл `vserence:onboarding`, раздел «Проект с нуля» — контракт и каркас с проверками (форматтер, линтер, проверка типов для типизированных языков, smoke-тест запуска) до первой строки бизнес-логики.
3. `vserence:risk-analyst` → `STATE stage plan` (`superpowers:writing-plans`) → `STATE stage tests`: тестовая инфраструктура и первый прогон в хуке (Stop-хук должен увидеть зелёные lint/typecheck/test_changed на каркасе).
4. Первая фича — по шагам режима feature начиная с этапа tests (`STATE stage tests` → `code` → `verify` → `review` → `report`).

### investigate
Чтение, замеры, гипотезы; правки кода запрещены (хук блокирует), тесты не трогаются.
1. Исследование через `vserence:explorer` и замеры командами без изменения файлов проекта.
2. Результат в `.vserence/tasks/<имя>/report.md` по скиллу `vserence:report`: гипотезы по убыванию вероятности; для каждой доказательство (замер, строка лога, место в коде) и способ проверить; рекомендуемая следующая задача с режимом.
3. `STATE stage report` → `STATE done`. Ревью для investigate не запускается.

## Стандарты: подгружай только затронутые направления
| Задача меняет | Скиллы |
| --- | --- |
| устройство модулей, новые модули, границы | `vserence:architecture-principles` |
| любые тесты (всегда при fix/feature/refactor/greenfield) | `vserence:testing-standards` |
| серверный код, фоновые задачи, внешние вызовы | `vserence:standards-backend` |
| схему БД, запросы, миграции, кэши | `vserence:standards-database` |
| HTTP/RPC API, вебхуки, форматы обмена | `vserence:standards-api` |
| права, вход/выход данных, секреты, зависимости, деньги, ПДн | `vserence:standards-security` (+ хуки security-guidance) |
| экраны, формы, компоненты | `vserence:standards-ui` + скилл `frontend-design` |
| домены из каталога рисков | `vserence:risk-catalog` (читает risk-analyst) |

Пример: задача про форму тянет UI и API, а не все стандарты. Отступление проекта от стандарта, записанное в `conventions.md` или `decisions/`, ошибкой не считается.

## Контекст
- Границы фаз = границы контекста: спецификация, план и отчёт пишутся в файлы задачи; реализация и ревью идут от файлов, а не от памяти диалога.
- Одна задача = одна сессия. Сжатие при заполнении 60% (`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=60` в настройках проекта): после сжатия SessionStart-хук возвращает имя задачи, этап и файлы; сохраняются спецификация, план, статус шагов и открытые замечания.
- Точечное чтение: сначала поиск и символы, потом нужный кусок файла. Исследование десятков файлов — в сабагенте `vserence:explorer`.

## 4. Проверки
- После каждой правки PostToolUse-хук запускает format и lint из `checks.json`; найденное исправляй сразу.
- При попытке закончить Stop-хук запускает lint, typecheck, test_changed и проверяет diff (skip/only/xfail, удалённые тесты, ослабленные проверки, ветки «если тестовое окружение»). Красное = работа продолжается: до 5 возвратов, потом статус «не завершено».
- Падения из `checks.json` → `baseline.known_failures` не красные: красное = падение, которого нет в baseline. Stop-хук сравнивает сам; полный `test` на этапе verify запускай через `STATE check test` (exit 2 = новые падения; результат пишется в `state.json` → `baseline_report`). Нераспознанный формат вывода = красное по коду выхода, и в отчёте «сравнение с baseline не выполнено».
- На этапе `verify` один раз запусти полные `test` (через `STATE check test`) и `build` из `checks.json`; если задача затрагивает критичные пользовательские пути из `project.md` — ещё `e2e`. Для изменённого кода критичных модулей — `mutation` (порог 70% убитых мутантов); нет инструмента — это делает ревьюер вручную.
- Тест упал, и ты считаешь неверным сам тест на этапе кода: не меняй его (хук заблокирует), `STATE incomplete "<почему тест неверный>"` и объясни в отчёте.

## 5. Ревью
Обязательно во всех режимах, кроме investigate; пропуск ревью = задача не завершена. Перед ревью закоммить всю работу в ветку задачи (ревьюер откатывает свои поломки через `git checkout -- <файл>`). Сабагент `vserence:reviewer` с чистым контекстом. В режиме fix вызывай его с параметром `model: "sonnet"`; в feature, refactor, greenfield — без параметра (opus из определения агента). Передай только: имя задачи, режим, путь к `spec.md` (для fix — текст задачи и описание симптома), базовый коммит `base_sha` из `state.json`. `rules.md` и `risks-analysis.md` ревьюер прочитает сам. Не передавай свои выводы о качестве.
- Вердикт «блокирует» → `STATE review-fail "<кратко>"` → исправляй (этап 3), затем снова проверки и ревью. Ревью возвращает работу до 2 раз; на третий раз скрипт ставит «не завершено».
- Вердикт «не блокирует» → замечания идут в отчёт как рекомендации.
- Если для ветки создан PR (`gh` настроен), дополнительно вызови `code-review:code-review` (плагин code-review) на этот PR; его замечания — рекомендации, если не входят в список блокирующих.

## 6. Завершение
0. Пост-шаги проекта, помеченные «сохраняется» в `conventions.md` → «Порядок с проектными правилами» (например, обновление графа кода), выполняются здесь, в ветке задачи, до отчёта.
1. Отчёт по скиллу `vserence:report` в `.vserence/tasks/<имя>/report.md`.
2. Коммиты в ветку задачи. Если задача поменяла модули, команды или решения — обнови контракт (`project.md`, `checks.json`, `decisions/`) тем же коммитом.
3. `STATE done`. В сессию выведи разделы «Итог», «Что сделано», «Что НЕ проверено» и путь к полному отчёту. Если для репозитория настроен `gh` или `glab`, отчёт идёт в описание PR (PR создаётся, но не мержится).
