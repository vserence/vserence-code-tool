# Роутер vserence

Скрипт состояния (единственный способ менять `state.json`): `node "${CLAUDE_PLUGIN_ROOT}/hooks/scripts/vserence-state.js" <команда>` — ниже `STATE`.
Файлы задачи: `.vserence/tasks/<имя>/` (spec.md, plan.md, risks-analysis.md, review.md, report.md). Они коммитятся в ветку задачи и никогда не читаются в других задачах.

## 1. Подготовка
Если в контексте есть инструкция SessionStart-хука об онбординге или синхронизации — сначала она (`vserence:onboarding`). Иначе сразу дальше.

## 2. Разбор задачи
1. Прочитай `.vserence/project.md` и `.vserence/conventions.md` (они короткие). Поиском (Grep/Glob, символы) найди объект изменения; для широкого поиска — сабагент `vserence:explorer`.
2. Выбери режим по таблице. Если режим задан явно (`/vserence <режим> …`), используй его.

| Режим | Когда |
| --- | --- |
| fix | есть наблюдаемый неверный результат, ожидаемое поведение известно, правка в одном модуле без смены контракта |
| feature | появляется новое поведение для пользователя или другой системы |
| refactor | вход и выход системы остаются прежними, меняется устройство кода или скорость |
| greenfield | проект или сервис с нуля |
| investigate | «почему тормозит», «откуда баг», аудит; правки кода запрещены |

3. **Подъём режима.** fix автоматически поднимается до feature, если правка затрагивает хотя бы одно: больше одного модуля из `project.md`, публичный API, схему БД, формат файлов или критичный модуль (список в `project.md`). Режим никогда не опускается. Подъём во время работы: `STATE escalate feature "<какой триггер>"`.
4. **Вопрос** задаётся, только если выполнено хотя бы одно условие:
   1. В задаче не назван объект изменения, и поиск по коду находит больше одного кандидата или ни одного.
   2. У задачи есть две трактовки, которые дают разное поведение для пользователя.
   3. Задача противоречит контракту или записи в `decisions/`.
   4. Нужны данные, которых нет в репозитории: лимиты, доступы, бизнес-правила.
   5. Нужно необратимое действие: удаление данных, миграция с потерей данных, смена публичного API.

   Про имена, стиль и всё, что решается конвенциями проекта, вопросы не задаются. Вопросы — одним сообщением, не больше трёх, у каждого варианты ответа. Перед вопросом: `STATE ask` (Stop-хук пропустит эту остановку). Это единственная обязательная остановка.
5. **Первая строка работы:** `Режим: <режим> — <почему, одной фразой>`, чтобы человек мог оспорить.
6. Создай задачу и ветку: `STATE start <короткое-имя-латиницей> <режим>` → ветка `vserence/<имя>`. Сборка никогда не мержит в основную ветку и не делает деплой: это решает человек.

## 3. Процесс режима

### fix
Модели: весь режим fix, включая ревью, — Sonnet.
1. Этап `tests`. Вызови скилл `superpowers:systematic-debugging`. Найди первопричину и всех вызывающих (Grep по символу; `vserence:explorer` для широкого поиска).
2. Сначала тест, воспроизводящий симптом: он падает по той причине, что описана в задаче. Закоммить тест отдельно: `test: воспроизведение <симптом>`.
3. `STATE stage code` (тесты заморожены хуком). Исправь в общей точке, а не в месте симптома. Если правка задела триггер подъёма — `STATE escalate feature "<триггер>"` и продолжай по режиму feature.
4. `STATE stage verify` → проверки (раздел 4) → `STATE stage review` → ревью (раздел 5) → `STATE stage report` → короткий отчёт (раздел 6).

## 4. Проверки
- После каждой правки PostToolUse-хук запускает format и lint из `checks.json`; найденное исправляй сразу.
- При попытке закончить Stop-хук запускает lint, typecheck, test_changed и проверяет diff (skip/only/xfail, удалённые тесты, ослабленные проверки, ветки «если тестовое окружение»). Красное = работа продолжается: до 5 возвратов, потом статус «не завершено».
- На этапе `verify` один раз запусти полные `test` и `build` из `checks.json`; если задача затрагивает критичные пользовательские пути из `project.md` — ещё `e2e`. Для изменённого кода критичных модулей — `mutation` (порог 70% убитых мутантов); нет инструмента — это делает ревьюер вручную.
- Тест упал, и ты считаешь неверным сам тест на этапе кода: не меняй его (хук заблокирует), `STATE incomplete "<почему тест неверный>"` и объясни в отчёте.

## 5. Ревью
Сабагент `vserence:reviewer` с чистым контекстом. В режиме fix вызывай его с параметром `model: "sonnet"`; в feature, refactor, greenfield — без параметра (opus из определения агента). Передай только: имя задачи, режим, путь к `spec.md` (для fix — текст задачи и описание симптома), базовый коммит `base_sha` из `state.json`. Не передавай свои выводы о качестве.
- Вердикт «блокирует» → `STATE review-fail "<кратко>"` → исправляй (этап 3), затем снова проверки и ревью. Ревью возвращает работу до 2 раз; на третий раз скрипт ставит «не завершено».
- Вердикт «не блокирует» → замечания идут в отчёт как рекомендации.
- Дополнительно для PR вызови скилл `code-review` из плагина code-review, если он доступен; его замечания — рекомендации, если не входят в список блокирующих.

## 6. Завершение
1. Отчёт по скиллу `vserence:report` в `.vserence/tasks/<имя>/report.md`.
2. Коммиты в ветку задачи. Если задача поменяла модули, команды или решения — обнови контракт (`project.md`, `checks.json`, `decisions/`) тем же коммитом.
3. `STATE done`. В сессию выведи разделы «Итог», «Что сделано», «Что НЕ проверено» и путь к полному отчёту. Если для репозитория настроен `gh` или `glab`, отчёт идёт в описание PR (PR создаётся, но не мержится).
