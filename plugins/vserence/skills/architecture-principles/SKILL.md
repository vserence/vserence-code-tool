# Принципы архитектуры

Критерии выбора решения, а не теория. Первоисточник: Ousterhout, «A Philosophy of Software Design».

## Принципы
1. **Направление зависимостей.** Бизнес-логика не зависит от фреймворка и БД: модули правил не импортируют HTTP-фреймворк, ORM и драйверы; доступ к ним — через интерфейс, который определяет сама бизнес-логика.
2. **Связность и зацепление.** Если одно изменение поведения требует правок больше чем в трёх модулях (по таблице модулей `project.md`), это признак неверных границ: запиши его в отчёт с предложением, как их исправить.
3. **Обратимость.** Дорогие к отмене решения — хранилище данных, схема БД, публичный API, внешний провайдер, формат файлов, границы модулей — записываются в `.vserence/decisions/` с обоснованием (шаблон в `decisions/README.md`).
4. **Согласованность.** Новое повторяет принятые в проекте паттерны. Отход разрешён только с записью в `decisions/`: что не так с текущим паттерном, чем лучше новый, где граница его применения.
5. **Владение данными.** У каждой сущности один владелец (модуль), остальные читают и меняют её через него.
6. **Простота.** Из двух рабочих вариантов выбирается тот, что проще объяснить. Новая абстракция (интерфейс, базовый класс, фабрика, параметр конфигурации) вводится, только если у неё есть два реальных использования в этом же изменении.
7. **Первопричина.** Исправление в общей точке, а не в месте симптома.
8. **Глубокие модули.** Простой интерфейс над сложной реализацией; сложность спрятана в одном месте; нет мелких проходных слоёв (функция/класс, который только передаёт вызов дальше с теми же аргументами).
9. **Ошибки исключены дизайном.** Где возможно, некорректное состояние невыразимо (тип, конструктор, значение по умолчанию), а не обработано проверками в каждом месте вызова.

## Как проверить
- [ ] `grep` импортов в модулях бизнес-логики: нет импортов фреймворка, ORM, драйвера БД.
- [ ] Число модулей из `project.md`, затронутых одним поведением, ≤ 3; иначе пункт в отчёте с предложением границ.
- [ ] Для каждого дорогого к отмене решения есть файл в `decisions/`.
- [ ] Каждая новая абстракция имеет ≥ 2 использования в diff.
- [ ] У каждой новой сущности назван один модуль-владелец в `project.md`.
- [ ] Нет новых функций, тело которых — один вызов с теми же аргументами.
- [ ] Исправление бага находится в функции, через которую проходят все вызывающие (проверено поиском вызовов).

## Антипаттерны
- «На будущее»: интерфейс с одной реализацией, фабрика для одного класса, параметр конфигурации без второго значения.
- Проверка одного и того же условия в каждом вызывающем вместо одной проверки в общей точке.
- Модуль A читает таблицы модуля B напрямую.
- Слой `Service → Manager → Handler`, где каждый только передаёт вызов.
- Новый паттерн «потому что лучше» без записи в `decisions/`.

## Плохо / хорошо
```text
ПЛОХО: симптом исправлен в одном месте
  controllerA: if price < 0 then price = 0      # баг всплывёт в controllerB, job C
ХОРОШО: инвариант в общей точке
  Price.create(v): if v < 0 then error "price must be >= 0"
  controllerA, controllerB, jobC используют Price.create
```
```text
ПЛОХО: бизнес-правило знает про ORM
  function applyDiscount(orderId): row = db.orders.find(orderId); row.total *= 0.9; row.save()
ХОРОШО: правило чистое, хранение снаружи
  function applyDiscount(order) -> order.with(total = order.total * 0.9)
  handler: order = repo.get(id); repo.save(applyDiscount(order))
```
