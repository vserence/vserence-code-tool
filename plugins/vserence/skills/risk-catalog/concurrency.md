# Конкурентный доступ

## 1. Потерянное обновление
- **Симптом:** изменение одного пользователя затирает изменение другого.
- **Причина:** чтение → изменение → запись целого объекта без контроля версии.
- **Как предотвратить:** оптимистичная блокировка (версия/updated_at в условии UPDATE) или атомарное обновление поля.
- **Как проверить тестом:** два параллельных обновления одной версии → одно успешно, второе получает конфликт.

## 2. Проверка-потом-действие (check-then-act)
- **Симптом:** остаток ушёл в минус, слот забронирован дважды.
- **Причина:** проверка условия и запись в разных операциях.
- **Как предотвратить:** условие в самом UPDATE/INSERT, уникальный индекс или блокировка строки.
- **Как проверить тестом:** N параллельных бронирований последнего слота → ровно одно успешно.

## 3. Взаимная блокировка
- **Симптом:** запросы падают с deadlock под нагрузкой.
- **Причина:** транзакции захватывают одни и те же строки в разном порядке.
- **Как предотвратить:** единый порядок захвата (по id), короткие транзакции, повтор при deadlock.
- **Как проверить тестом:** две транзакции, меняющие A и B в разном порядке, параллельно → обе завершаются (с повтором), данные корректны.

## 4. Двойная отправка формы
- **Симптом:** два одинаковых заказа/комментария.
- **Причина:** повторный клик или повтор запроса клиентом.
- **Как предотвратить:** ключ идемпотентности, блокировка кнопки на время запроса.
- **Как проверить тестом:** два одинаковых запроса параллельно с одним ключом → одна запись.
